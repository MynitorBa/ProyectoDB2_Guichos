1. ¿Qué es TiendaYa?

TiendaYa es un marketplace guatemalteco de compra y venta en línea. Funciona como una sola plataforma donde vendedores publican productos de categorías muy distintas (electrónica, ropa, alimentos, libros…) y compradores los buscan, agregan al carrito y pagan.

El proyecto es a la vez un sistema funcional y una demostración académica de persistencia polígota: usa dos bases de datos distintas, cada una para lo que hace mejor, conectadas por una API en Python.

3. MySQL — datos relacionales

MySQL guarda todo lo que tiene estructura fija y relaciones bien definidas: usuarios, pedidos, direcciones, métodos de pago. Son datos transaccionales que necesitan integridad referencial (un pedido no puede existir sin un usuario válido) y operaciones ACID.

Tablas principales

  • usuarios — credenciales, roles, estado
  • direcciones — FK a usuario
  • productos_catalogo — SKU, precio, disponibilidad
  • pedidos — total, estado, FK a usuario y dirección
  • pedido_items — qué productos y cuántos
  • metodos_pago — catálogo de formas de pago

Por qué MySQL aquí

  • Los datos son tabulares y muy relacionados entre sí
  • El checkout necesita atomicidad (o todo o nada)
  • Los usuarios y pedidos no cambian de esquema
  • Las consultas son predecibles y usan JOINs
  • El stock se decrementa en un stored procedure transaccional

Stored procedure de checkout atómico

El checkout completo (validar stock, crear pedido, decrementar inventario) vive en un único stored procedure de MySQL. Se llama desde Python con una sola instrucción CALL sp_checkout(...). Si cualquier paso falla, la transacción completa hace rollback automático.

-- Resumen simplificado del flujo interno del SP
BEGIN TRANSACTION;
  -- 1. Validar stock por cada ítem
  IF stock_insuficiente THEN ROLLBACK; END IF;
  -- 2. Crear fila en `pedidos`
  INSERT INTO pedidos ...;
  -- 3. Insertar cada ítem en `pedido_items`
  INSERT INTO pedido_items ...;
  -- 4. Decrementar stock en `productos_catalogo`
  UPDATE productos_catalogo SET stock = stock - cantidad ...;
COMMIT;
Decisión de diseño Mover el checkout al motor de base de datos elimina la posibilidad de que un crash de la API deje el sistema en un estado inconsistente (pedido creado pero stock sin decrementar). El SP o completa todo o no hace nada.

4. MongoDB — catálogo y eventos

MongoDB guarda el catálogo de productos (con atributos variables por categoría) y el historial de cambios de cada producto. Son datos que no caben bien en tablas fijas.

El problema de los atributos variables

Una laptop tiene procesador, RAM, almacenamiento. Una camisa tiene talla, color, material. Un libro tiene autor, ISBN, editorial. No comparten ningún campo. En MySQL necesitarías un diseño EAV (Entity-Attribute-Value) muy complicado. En MongoDB cada producto es un documento JSON con sus propios campos:

// Laptop en MongoDB
{
  "_id": "64abc...",
  "nombre": "ThinkPad X1 Carbon",
  "precio": 8500,
  "categoria": { "slug": "computadoras" },
  "atributos": {
    "procesador": "Intel Core i7-1365U",
    "ram_gb": 16,
    "almacenamiento_gb": 512,
    "pulgadas": 14
  }
}

// Camisa en MongoDB — mismo esquema raíz, atributos distintos
{
  "_id": "64def...",
  "nombre": "Camisa Oxford Slim",
  "precio": 180,
  "categoria": { "slug": "camisas" },
  "atributos": {
    "talla": "M",
    "color": "azul marino",
    "material": "algodón 100%"
  }
}

Event sourcing: historial de cambios

La segunda colección en MongoDB es producto_eventos. Cada vez que un administrador modifica un producto, en lugar de sobreescribir el documento, se agrega un nuevo evento con el estado anterior y el nuevo. La colección es append-only (solo se insertan, nunca se borran).

// Ejemplo de evento de precio actualizado
{
  "_id": "ObjectId(...)",
  "producto_id": "64abc...",
  "tipo_evento": "PRECIO_ACTUALIZADO",
  "version": 3,
  "timestamp": "2026-06-15T10:30:00Z",
  "datos_anteriores": { "precio": 8200 },
  "datos_nuevos":     { "precio": 8500 }
}

Tipos de eventos registrados:

Tipo de eventoCuándo se dispara

PRECIO_ACTUALIZADOCambio en el campo precio

Reconstrucción del estado en una fecha

Dado que todos los cambios están guardados como eventos, se puede reconstruir cómo era un producto en cualquier fecha del pasado: se toma el primer evento (PRODUCTO_CREADO) y se aplican secuencialmente todos los eventos que ocurrieron antes de la fecha solicitada.

# Lógica de reconstrucción (Python simplificado)
def get_state_at(producto_id, fecha):
    eventos = mongo.producto_eventos.find(
        {"producto_id": producto_id,
         "timestamp": {"$lte": fecha}},
        sort=[("timestamp", ASC)]
    )
    estado = {}
    for evento in eventos:
        estado.update(evento["datos_nuevos"])
    return estado
Por qué MongoDB para el historial Con MySQL necesitarías una tabla de auditoría con columnas campo, valor_anterior, valor_nuevo de tipo VARCHAR — y perderías los tipos. MongoDB guarda el objeto completo como JSON, preservando el tipo de cada campo (precio es un número, no un string).

5. La migración: de MySQL a MongoDB

Los 65 productos del seed original estaban en MySQL en la tabla productos_catalogo. Esta tabla tiene columnas fijas: nombre, precio, descripcion, categoria_id. Los atributos variables (RAM, talla, ISBN…) estaban codificados como texto en la columna descripcion con el formato:

"procesador: Intel Core i7 | ram_gb: 16 | almacenamiento_gb: 512 | pulgadas: 14"

¿Qué migra el script?

El script backend/scripts/migrate_products_to_mongo.py hace lo siguiente:

  1. Lee todos los productos de MySQL con un JOIN a la tabla categorias
  2. Parsea el texto de descripcion con la función _parse_desc() que convierte "clave: valor | ..." en un diccionario Python
  3. Construye el documento MongoDB con la estructura anidada correcta, incluyendo el subdocumento atributos con los tipos correctos (números como números, booleanos como booleanos)
  4. Inserta o actualiza en MongoDB usando bulk_write con operaciones UpdateOne(..., upsert=True), lo que hace el script idempotente (se puede ejecutar múltiples veces sin duplicar datos)
  5. Por cada producto migrado, registra un evento PRODUCTO_CREADO en la colección producto_eventos
Entrada
MySQL: productos_catalogo × categorias 65 filas con atributos en texto plano
Proceso
Parse de descripción → extractores por categoría _extraer_laptop(), _extraer_ropa(), _extraer_libro()…
Salida
MongoDB: colección productos + producto_eventos 65 documentos con atributos tipados + 65 eventos PRODUCTO_CREADO

¿Por qué no se eliminan los productos de MySQL?

Intencionalmente. La tabla productos_catalogo de MySQL sigue siendo la fuente de verdad para precio, stock y disponibilidad porque estos datos participan en el checkout transaccional. MongoDB tiene una copia enriquecida para el catálogo y la búsqueda, con los atributos específicos de cada categoría. La sincronización entre ambas bases de datos la maneja la API.

6. El backend: FastAPI

FastAPI es el mediador central. Conecta con MySQL vía SQLAlchemy (ORM) y con MongoDB vía PyMongo (driver nativo). Expone una API REST bajo el prefijo /api.

Autenticación con JWT

Al hacer login, FastAPI verifica la contraseña con bcrypt.checkpw() y genera un JWT firmado con la clave secreta del servidor. El token tiene un tiempo de expiración configurable (por defecto 7 días). Todos los endpoints privados usan el decorador Depends(get_current_user) que extrae y verifica el token automáticamente.

7. El frontend: React + Tailwind v4

El frontend es una SPA (Single Page Application) construida con React 18 y Vite. Toda la comunicación con el backend pasa por funciones en la carpeta src/api/ que usan Axios con un interceptor que adjunta automáticamente el token JWT.

Sistema de diseño

El diseño usa Tailwind CSS v4, una versión que funciona diferente a las anteriores: en lugar de un archivo de configuración JavaScript, los tokens de diseño se definen directamente en el CSS con el bloque @theme.

8. Decisiones de diseño

¿Por qué dos bases de datos en lugar de solo una?
MySQL es excelente para datos relacionales y transacciones ACID. MongoDB es excelente para documentos con esquema variable. Los productos de TiendaYa tienen exactamente esa dualidad: la parte transaccional (pedidos, stock) pertenece a MySQL; la parte de catálogo con atributos heterogéneos pertenece a MongoDB. Usar solo MySQL obligaría a un diseño EAV complejo. Usar solo MongoDB haría el checkout más difícil de garantizar como atómico.
¿Por qué event sourcing para el historial de productos?
Una tabla de historial clásica guardaía solo el valor nuevo de cada campo. Event sourcing guarda el estado anterior y nuevo, más un tipo de evento semántico. Esto permite: (1) saber exactamente qué cambió y cuándo, (2) reconstruir el estado completo del producto en cualquier fecha pasada, (3) hacer auditoría visual clara. El costo es almacenamiento adicional, pero a 65 productos con ~7 eventos promedio, es completamente manejable.
¿Por qué bcrypt directo en lugar de passlib?
passlib 1.7.4 (la versión estable) es incompatible con bcrypt 4.x y 5.x porque internamente llama a detect_wrap_bug() con una contraseña de más de 72 bytes, y las versiones nuevas de bcrypt rechazan eso. La solución fue usar bcrypt.hashpw() y bcrypt.checkpw() directamente, que son más simples y no tienen esa limitación.
¿Por qué el checkout es un stored procedure y no lógica Python?
Mover el checkout al motor de base de datos garantiza atomicidad incluso si el proceso Python se cae a mitad de la operación. Un stored procedure corre dentro de una transacción que MySQL gestiona completamente. Si algo falla, el rollback es automático. Con lógica en Python, habría que manejar el rollback manualmente y siempre existe la posibilidad de un estado inconsistente.
¿Por qué Tailwind CSS v4 en lugar de v3?
Tailwind v4 integra directamente con Vite sin necesidad de PostCSS, lo que simplifica la configuración. Los tokens de diseño se definen como variables CSS nativas en @theme{}, lo que significa que son accesibles desde cualquier parte del CSS con var(--color-action), no solo desde clases de Tailwind. El dark mode se implementa con selector CSS puro (.dark { }) sin necesidad de configuración especial.

9. Cómo correr el proyecto

# 1. Levantar las bases de datos (Docker)
docker compose up -d

# 2. Iniciar el backend
cd backend
pip install -r requirements.txt

# 3. Iniciar el frontend
cd frontend
npm install
npm run dev        # arranca en localhost:5173

Nota sobre el script de migración El script backend/scripts/migrate_products_to_mongo.py ya fue ejecutado durante la configuración inicial. Los 65 productos y sus eventos ya están en MongoDB. Si se necesita volver a ejecutar, usar la bandera --reset para limpiar la colección antes de migrar.
